# Direct raw CT/MRI image input (research starter)

This optional path lets a 3D CNN read medical image volumes directly instead of requiring hand-crafted columns such as `imaging_score`, `lesion_area`, `atrophy_index`, and `tissue_change`.

## Supported inputs

- A 3D NIfTI file: `.nii` or `.nii.gz`
- A directory containing exactly one DICOM series

A single 2D PNG/JPG slice is not supported by this 3D script. DICOM folders with multiple series must be separated so each manifest row points to the intended series directory.

## Required labelled manifest

Copy `raw_images_manifest_template.csv` to `raw_images_manifest.csv` and fill one row per scan:

| Column | Required meaning |
|---|---|
| `patient_id` | Stable pseudonymous patient identifier; same person must use the same ID at every visit |
| `image_path` | Path to a NIfTI file or a directory containing one DICOM series; relative paths are resolved from the manifest directory |
| `stage` | Verified label coded as integer 0, 1, 2, or 3 |
| `visit_idx` | Optional visit sequence number, useful for organising repeated scans |

The stage labels are **not generated by this script**. Use only labels defined by your dataset documentation or clinical/research protocol. Do not copy the illustrative labels from the synthetic demo into a real-data manifest. If your dataset uses different labels, define a documented mapping before training rather than silently recoding them.

Example structure only (not real data):

```csv
patient_id,image_path,stage,visit_idx
SUBJECT_A,images/SUBJECT_A/scan0.nii.gz,0,0
SUBJECT_B,images/SUBJECT_B/scan0.nii.gz,1,0
```

Replace every example path and label with valid values from an authorised dataset. At least 10 distinct patients are required for the default patient-level split, but that minimum is not evidence that a dataset is large enough for reliable model development.

## Run locally

Install dependencies, prepare the manifest and image files, then run:

```bash
python -m pip install -r requirements.txt
python train_raw_image_model.py --manifest raw_images_manifest.csv --modality generic
```

For a small smoke run on a suitably prepared dataset:

```bash
python train_raw_image_model.py --manifest raw_images_manifest.csv --epochs 2 --batch-size 1 --image-size 32 --modality generic
```

The script writes a versioned `raw_image_3dcnn.pt` checkpoint, training history and run summary to `raw_image_results/`. The checkpoint contains model weights, architecture/version metadata, and the exact image preprocessing settings used at training time. Test metrics are only meaningful for the supplied labelled dataset and patient split.

## Image-only checkpoint inference

To run inference after training, create a separate CSV with one row per scan. Only `patient_id` and `image_path` are required; `visit_idx` and `time_months` are optional. Ground-truth `stage` labels are not required for prediction.

```csv
patient_id,image_path,visit_idx,time_months
SUBJECT_A,images/SUBJECT_A/followup.nii.gz,1,6
SUBJECT_B,images/SUBJECT_B/baseline.nii.gz,0,0
```

Run:

```bash
python predict_raw_image_model.py --checkpoint raw_image_results/raw_image_3dcnn.pt --manifest prediction_manifest.csv --output predictions.csv
```

Relative image paths are resolved from the prediction manifest's directory. The CLI uses the checkpoint's saved modality, voxel size, target spacing and CT window values; it intentionally does not offer inference-time overrides that could silently make preprocessing differ from training. The output includes `predicted_stage`, `confidence`, and `prob_stage_0` through `prob_stage_3`. Probabilities are model outputs and are not necessarily calibrated. Older weights-only checkpoints cannot be used by this CLI because they do not record preprocessing metadata; retrain with the current trainer to create a compatible artifact.

The artifact format is versioned. Keep the checkpoint together with its training manifest provenance, run summary, dependency environment, and the relevant source revision. Do not load checkpoints from untrusted sources.

### Modality and intensity preprocessing

- Default `--modality generic`: clips each volume to its own 1st–99.5th intensity percentiles and standardizes it.
- `--modality mri`: uses the same generic per-volume percentile policy as a basic starting point; MRI protocols can require more careful bias-field correction, registration, or normalization.
- `--modality ct`: clips to the configured intensity window, then standardizes. Example command: `python train_raw_image_model.py --manifest raw_images_manifest.csv --modality ct --ct-window-low -1000 --ct-window-high 1000`. This window is only an example, not a universal CT setting; choose bounds based on anatomy and task and confirm pixel values are in Hounsfield units.

**Physical-space preprocessing:** the loader reorients volumes to LPS and, by default, linearly resamples them to isotropic 1.5 mm voxels before converting them to a fixed-size input. Set this with `--target-spacing-mm` (for example, `--target-spacing-mm 2.0`). After intensity normalization, it center-crops or pads each axis to the requested cube; it does not stretch each axis independently. This can still crop anatomy or add background, and the target spacing/field of view must be selected for the anatomy and task. Check image orientation, origin, spacing, pixel-value conventions and the resulting field of view on your dataset before training.

## Longitudinal multimodal fusion (raw scans + tabular visits)

Use `train_multimodal_raw_image_model.py` when each visit has both a raw scan and tabular clinical, treatment, medicine, or wearable measurements. Unlike the image-only script above, this path encodes each raw scan with a 3D CNN, fuses its embedding with the available tabular values and explicit missingness masks, and uses a causal Transformer over that patient's visits.

Start with [`multimodal_raw_manifest_template.csv`](multimodal_raw_manifest_template.csv). The template uses `C_` for clinical, `T_` for treatment, `M_` for medicine, and `W_` for wearable features. Required columns:

- `patient_id`: stable pseudonymous patient identifier.
- `image_path`: one 3D NIfTI file or one-series DICOM directory per visit.
- `stage`: verified integer label 0–3 for that visit.
- `visit_idx`: unique visit order per patient.
- `time_months`: optional numeric time relative to the patient's baseline; if omitted, `visit_idx` is used.
- At least one numeric tabular feature column. The template uses group prefixes: **C_ = clinical**, **T_ = treatment**, **M_ = medicine**, and **W_ = wearable**. The training script accepts any numeric feature column with one of these prefixes, so you can rename columns to match your dataset without editing the model code. Older unprefixed demo columns are still accepted for backward compatibility. Columns can be omitted if unavailable; missing values in included columns are represented with observation masks. Feature scaling is fit on training patients only.

### Replacing the demo columns with your real dataset

The prefixes are a naming convention to keep the CSV organised; they do not transform or validate the meaning of a variable.

| Prefix | Group | Example |
|---|---|---|
| `C_` | Clinical | `C_hemoglobin`, `C_age`, `C_bmi` |
| `T_` | Treatment | `T_treatment_duration_days` |
| `M_` | Medicine | `M_dose_per_day` |
| `W_` | Wearable | `W_steps`, `W_sleep_hours` |

If your real data has the **same columns and encodings**, copy the template and replace the example values, patient IDs, image paths, and verified stage labels. If your dataset has different numeric measurements, rename those feature columns using the correct prefix (for example, `C_hemoglobin`) and keep the required columns `patient_id`, `image_path`, `stage`, and `visit_idx`. You do not need to edit the model code just to add a new numeric feature with one of the four prefixes. For prediction, use the same feature names and encodings that were used for training; the checkpoint records the training feature columns.

**Numeric and categorical data are both supported.** You may enter age as a number (for example, `C_age=45`), sex as text (for example, `C_sex=Female` or `C_sex=Male`), and medicine names as text (for example, `M_medicine_name=Metformin`). During training, the pipeline learns category vocabularies from training patients only and converts categorical columns into one-hot features. At prediction time it reuses the saved mappings; an unseen category is handled with an unknown-category feature, and a missing value remains missing. You do not need to manually encode these text categories.

Use one consistent spelling for each category where possible, keep measurement units consistent, and document what each variable means. The code does not infer medical equivalence between different medicine names or spellings. Keep feature names consistent between training and prediction. Use only data you are authorised to process, and retrain the model when the training data or feature definitions change.

Run:

```bash
python train_multimodal_raw_image_model.py --manifest multimodal_raw_manifest.csv --modality generic
```

For a small smoke run on a suitably prepared dataset:

```bash
python train_multimodal_raw_image_model.py --manifest multimodal_raw_manifest.csv --epochs 1 --batch-size 2 --image-size 16 --target-spacing-mm 1.0
```

The model checkpoint includes its feature-column order, training-only feature statistics, image size, target spacing, modality settings and architecture identifier. The output directory also contains training history and a JSON run summary with held-out test metrics.

To generate per-visit predictions from a saved checkpoint, prepare a CSV with `patient_id`, `image_path`, `visit_idx`, optional `time_months`, and the same feature columns used for training (unavailable feature columns may be omitted and are treated as missing):

```bash
python predict_multimodal_raw_image_model.py --checkpoint multimodal_raw_results/multimodal_raw_model.pt --manifest prediction_manifest.csv --output predictions.csv
```

The output CSV includes the predicted stage, confidence, and four class probabilities per visit. This is a research prediction interface, not a clinical decision tool.

**Important:** this performs causal sequence classification of supplied visit-stage labels. It is not a validated future-outcome forecast. Patient-level splitting reduces patient leakage, but does not remove confounding, site/scanner shift, label errors, or small-sample uncertainty. No real medical data or clinical performance is supplied by the repository.

## Scientific and technical limitations

- These scripts are research baselines, not clinical tools or validated diagnostic models.
- The image-only script predicts the supplied stage label from one scan. The separate multimodal script fuses raw-image embeddings with available clinical, wearable, medicine and treatment features over visits; neither is clinically validated.
- The default per-volume intensity normalization is generic. CT Hounsfield-unit windowing, MRI-specific intensity handling, orientation, voxel spacing, resampling and scanner/site differences need modality-specific review.
- Isotropic resampling and center crop/padding improve geometric consistency but do not guarantee that the same anatomy is present in every input. Inspect the field of view and potential cropping for the target task.
- A patient-level split prevents scans from the same listed patient appearing across partitions, but does not address all confounding, site leakage, label errors, or distribution shift.
- The script does not create segmentation masks or extract lesion-specific features.
- No performance claim can be made until it has been run and evaluated on a permitted, correctly labelled dataset.
